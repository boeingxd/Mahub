# 0002. Login: our own Google sign-in

- Status: accepted, amended by ADR 0008 (session cookie instead of `auth_sessions`)
- Date: 2026-10-09

## Context
Students and instructors sign in with Google accounts. The predecessor used Supabase Auth, whose behaviour we couldn't see or control.

## Decision
- Google OpenID Connect via the `openid-client` library. We don't write our own crypto.
- The server verifies the ID token, then decides who may sign in. The rules are in ADR 0007, which replaced the original "email domain check".
- Login sessions are stored in Postgres (`auth_sessions`, which keeps only a hash of the token). The browser holds the token in an `HttpOnly`, `Secure`, `SameSite=Lax` cookie.

## Alternatives considered
- **Supabase Auth:** familiar, but it adds a second auth system and its tokens would have to be mapped into our RLS.
- **Keycloak:** too heavy for a team of three.

## Consequences
- We build logout, session expiry and CSRF protection ourselves (small, but it must be done).
- We control exactly how `user_id` reaches RLS (`SET LOCAL app.user_id`).
